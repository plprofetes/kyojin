# Dynamic ("shared") GPU memory on Strix Halo: why models stop loading at ~40 GiB

Date: 2026-11-20. Machine: Ryzen AI Max+ 395, Radeon 8060S (gfx1151), 128 GB, Windows 11 Pro build 26300, AMD driver 32.0.32015.7029, torch 2.15.0a0+rocm10.1.0a20260822, HIP 7.16.26332.
Tags: **[V]** measured in this session, **[S]** stated by a source (not verified here), **[I]** inference, **[?]** unknown.

## Current status (end of 2026-11-20, after Adrenalin 26.11.2 + chipset update)

1. **Cause of the model stop at ~40 GiB (original question):** two stacked problems, both reproducible. (a) Reporting: the stock runtime (`amdhip64_7.dll` 10.0.3581.0 from wheel `rocm 10.1.0a20260822`) reports a 76.79 GiB total with 2:1 accounting, so the loader's headroom check (`model_ls.py:282`) refuses at ~38 GiB; fixed upstream in rocm-systems #10974/#13193 (a locally built runtime shows 98.22 GiB, 1:1) but no public Windows wheel contains the fixes yet. (b) Residency: with `alwaysResident_` (HIP default) every allocation must be resident at each GPU submit; Windows refuses at about **61 GiB** allocated (`PAL ... result:-5`, `ErrorOutOfGpuMemory`, then error 719), even for untouched memory and with 41 GiB of RAM free.
2. **Reproduced without torch, in C++:** `scripts/windows/probes/hip_wall.cpp` (hipMalloc N GiB untouched, then one tiny kernel): N=40 ok, N=65 and N=80 fail with 719 (stock runtime, driver 26.11.2); with `PAL_ALWAYS_RESIDENT=0` N=40, 65, 80 all ok **[V]**. So the wall and the lever are properties of the runtime/driver, not of torch.
3. **Lever found:** `PAL_ALWAYS_RESIDENT=0` (HIP runtime flag, `palsettings.cpp:411`) removes the wall for compute (torch and C++: 80 to 95 GiB allocated, kernels ok) **[V]**.
4. **Why `PAL_ALWAYS_RESIDENT=0` fails in the real load (solved, reproduced in C++):** with the flag off HIP only keeps resident the buffers that are passed as *direct pointer arguments* of a kernel (per-command reference tracking); a kernel that receives its pointers *inside a by-value struct* (torch's `std::array<char*,N>` TensorIterator arguments, i.e. nearly every torch elementwise kernel) touches buffers HIP does not know about, and the GPU takes a page fault (PAL result -87, then error 719). `scripts/windows/probes/hip_fresh_alloc.cpp`: 8 and 16 MiB fresh `hipMalloc` buffers, fp16 -> fp32 kernel, flag off: direct pointer args **ok**, pointers in a struct **FAIL at rep 1 with 719**; flag on: both ok **[V]**. The earlier "all fine" tests passed only because the touched buffers happened to be resident. So the flag is not a workaround: it trades the 61 GiB residency wall for random GPU page faults. **Caveat [V]:** the struct-pointer explanation is supported but incomplete: a single struct-pointer kernel on fresh buffers passes with the flag off (`hip_ops_after_alloc.cpp kernel_struct` and `struct_after_submit`); the failure needs a second round (`hip_fresh_alloc.cpp`, rep 1) or torch's allocation pattern, so the exact residency rule is not known. The first failing op in the real load (`hyperconnections.py:638`, `w_h.float()`) is just the first torch kernel to hit a non-resident buffer. Isolated torch repro: `hcp2.py convert_only` (fp16 randn of 3.3M elements, `.float()` twice) fails after 1 iteration with the flag off; 4 to 16 MiB fp16 -> fp32 fail, <= 2 MiB pass (size/segment dependent, not understood) **[V]**.
5. Rollback info, per-state versions and test matrix: [versions-and-rollback.md](versions-and-rollback.md). Bug-report drafts: [amd-bug-report-draft.md](amd-bug-report-draft.md) (do not yet mention the flag or the C++ repro; add before filing).


### Decomposition of the loader failure with `PAL_ALWAYS_RESIDENT=0` (2026-11-20, Adrenalin 26.11.2) **[V]**

Instrumented run (stock runtime): `PAL_ALWAYS_RESIDENT=0 AMD_SERIALIZE_KERNEL=3 AMD_SERIALIZE_COPY=3 AMD_LOG_LEVEL=3 EXL3_LOAD_DIAG=1`, measuring forward skipped (`autosplit_no_forward`, via an import hook), fails within 2 s:

- First failing launch: `at::native::vectorized_elementwise_kernel<... float16tofloat32_copy_kernel_cuda ...>` (a torch `.half().float()` conversion), grid {5,1,1} x {256,1,1}; Python frame `exllamav3/modules/hyperconnections.py:638` (`tmp *= self.w_h.float()` in `_prepare`, called from `HyperConnections.load` line 613, module 2 of the model; module 1, `hc_expand`, loaded fine). At that moment only 0.15 GiB are allocated by the process.
- PAL result for that submit: **-87 = `ErrorGpuPageFaultDetected`** (`palUtil.h:472`), then -28 (incomplete command buffers), `hipErrorLaunchFailure`. So with the flag off the GPU takes a **page fault**, not an out-of-memory.
- Not reproduced outside the real load with the flag off: 80 GiB allocated then `fill_` on first/middle/last buffers (ok); 3000 small `empty().normal_().float()` allocations of mixed sizes (ok); direct `stloader_read` and `SafetensorsCollection.get_tensor` of 320 tensors (ok); C++ copy-engine mimic (ok). So the faulting access depends on state created earlier in the real load (suspects: module 0/1 work, pinned/host-mapped buffers of the n-gram/embedding modules, tensors written by the loader's own streams and then read by a torch kernel without a device-wide sync, `g_tensor_cache` scratch). Not isolated yet **[?]**.
- Resolution of the open point: see status item 4 (pointers inside kernel argument structs are not tracked when `alwaysResident_` is off; reproduced in pure C++ with `hip_fresh_alloc.cpp`). The module bisect (`GatedDeltaNet` / `HyperConnections`) merely shows where the first torch kernel on a non-resident buffer happens **[V]**.

## Operation test at 80 GiB allocated (pure C++, stock runtime, driver 26.11.2) **[V]**

`scripts/windows/probes/hip_ops_after_alloc.cpp`: allocate 80 x 1 GiB untouched, then one operation on a fresh 64 MiB buffer, one process per op, 75 s timeout.

| Operation | `PAL_ALWAYS_RESIDENT=1` (default) | `PAL_ALWAYS_RESIDENT=0` |
|---|---|---|
| `hipMalloc` 64 MiB + sync | ok | ok |
| `hipMemset`, `hipMemsetAsync`, D2D, H2D, D2H copy | **hang (no result in 75 s)**; an unguarded run sat 10 minutes with the process working set at 79.2 GiB and no CPU use | ok |
| kernel, direct pointer args | **hang** | ok |
| kernel, pointers in a struct | **hang** | ok |

- With the default flag, GPU work submitted while 80 GiB are allocated does not fail with an error here, it never completes (earlier `hip_wall.cpp` runs failed with 719 at 65 and 80 GiB: the outcome is a hang or error 719, run to run). The earlier raw `hipMemset` loop that reached 101 GiB allocates and touches in 1 GiB steps, so each submit only has to make the newly touched memory resident; "allocate everything first, then submit" needs all 80 GiB resident at once **[I]**. The wall is therefore about what must be resident *at a submit*, which is every live allocation when `alwaysResident_` is on.
- Why VidMm hangs in one run and returns an error in another is unknown **[?]**.

## VMM path test (`hipMemAddressReserve` + `hipMemCreate` + `hipMemMap` + `hipMemSetAccess`) **[V]**

`scripts/windows/probes/hip_vmm.cpp`, stock runtime, driver 26.11.2, `VirtualMemoryManagementSupported = 1`, granularity 64 KiB:

| Run | Result |
|---|---|
| default flag, 1 GiB chunks, map + touch each (ladder to 80 GiB) | `hipMemMap` of chunk 31 fails: error 719 (about **31 GiB** mapped) |
| default flag, 1 GiB chunks, map 80 GiB first then one memset | `hipMemMap` chunk 31: 719 |
| default flag, 1 GiB chunks, map first then tiny kernel | `hipMemMap` chunk 31: 719 |
| default flag, 100 GiB ladder | `hipMemMap` chunk 31: 719 |
| default flag, 256 MiB chunks | `hipMemMap` chunk 124: 719 (again about 31 GiB) |
| default flag, 4 GiB chunks | 719 at the first touch/sync |
| `PAL_ALWAYS_RESIDENT=0`, 1 GiB chunks, map 80 GiB then memset | ok |

- The VMM path hits a wall at **half** the `hipMalloc` figure (about 31 GiB instead of 61), independent of chunk size and of touching. Source check **[V]**: clr adds exactly one `AddGpuMemoryReferences(..., CantTrim)` per physical allocation (`palresource.cpp:35-41`, `hipMemCreate` path) and none in `hipMemMap` (`Device::virtualMap`, `paldevice.cpp:2615-2675`: `RemapVirtualMemoryPages` only); the wall does not depend on the reserved VA size (N=80 and 100 fail at the same chunk). So there is **no patchable double add in clr**; the second charge, if any, is in PAL or the kernel-mode driver **[?]**.
- With the flag off, VMM maps 80 GiB without error, as `hipMalloc` does; the safety concern (untracked pointers fault) is unchanged.
- Conclusion: VMM is not a way around the wall on this runtime; it makes it worse. Still untested allocation paths: pinned allocation types and `hipMallocAsync` / memory pools. Add this result to the bug reports (VMM allocations are charged twice against the residency limit).

## Possible solutions (2026-11-20), ranked by value for effort

Constraint today: with `alwaysResident_` (default), device allocations plus pinned host memory (pageable host memory counts about half) must stay under about 61 GiB in dynamic mode; the flag-off mode is unsafe; no AMD fix exists; the fixed carve-out has no such limit.

| # | Option | What it does | Status | Cost / risk |
|---|---|---|---|---|
| 1 | **Fixed carve-out sized to the model** (for example 72 to 80 GB for Flash-Next 4.05bpw: 64 GiB weights + KV + headroom) | Allocations come from the carve-out (Local heap, always resident, no 61 GiB policy); Windows keeps 47 to 55 GB instead of 32 GB | 96 GB measured good earlier **[V]**; 72 to 80 GB untested | Reboot per change; less RAM for Windows than dynamic; contradicts the wish for dynamic mode |
| 2 | **Stay under the wall in dynamic mode**: smaller quant or fewer device-resident weights (Flash-Next 3.05bpw, 35B, 27B) | Keeps device + pinned memory below about 55 GiB | 35B/27B fit **[V]**; 3.05bpw device size not checked **[?]** | Quality/speed trade; no code |
| 3 | **Use the repo's expert tiering** (`EXL3_EXPERT_BUDGET_GIB`, `exllamav3/modules/expert_store.py`): hot experts in a device slot pool (about 45 to 50 GiB), cold experts in host memory | Pageable host memory counts half against the wall, so about 20 GiB of cold experts cost about 10 | Code exists (written for Linux unified memory); not tried on Windows **[?]** | Needs a test run; decode speed depends on hit rate; if host experts end up pinned they count 1:1 |
| 4 | **Other allocation paths: VMM (`hipMemCreate`/`hipMemMap`)** | A different physical-allocation path might not be on the always-resident list | **Tested, worse:** `hipMemMap` fails with 719 after about 31 GiB mapped, any chunk size, with or without touching; flag off maps 80 GiB **[V]**. | 6 | **Use the locally built runtime** (`C:\Users\plpro\.kyojin\hip-build`) | Fixes the 2:1 `mem_get_info` and the 76.79 GiB total, so the loader check passes | Built and tested **[V]**; does not move the 61 GiB wall | Wheel stays stock; DLL preloaded by hand |

Suggested order: 4 (small C++ test, cheap, could change a lot), 3 and 2 (stay in dynamic mode today), 5 (fold findings into the reports), 1 as the fallback when a model must exceed about 55 GiB on the device.

## What changed and what broke

- Before: 96 GB dedicated GPU memory (Windows saw 31.6 GB RAM). `torch.cuda.mem_get_info()` total 107.87 GiB; Flash-Next 4.05bpw (64 GiB of weights on the GPU) and the 122B loaded fine.
- Now: dynamic / shared mode. Windows sees 127.1 GiB RAM, Task Manager "dedicated" is about 0.1 to 0.3 GiB **[V]**. `mem_get_info` total is **76.79 GiB** (free 76.63) **[V]**.
- `serve-flash-next.ps1` stops with `RuntimeError: Insufficient VRAM in split for model and cache` after about 38 GiB of weights (layer 28 of 40-ish) **[V]**. Run folder: `logs/windows/20261120-092800-serve`.

## Measurements

1. **The loader's refusal is a Python check, not a real out-of-memory.** `exllamav3/model/model_ls.py:282-291` reads `torch.cuda.mem_get_info()` after every layer and raises `OutOfMemoryError` when `free + reserved - allocated < largest transient + EXL3_AUTOSPLIT_MARGIN_MB`. `EXL3_LOAD_DIAG=1` plus a trace of that call (`scripts/windows/probes/serve_with_mgi_trace.py`, full log `doc/windows/logs-shared-vram-20261120-load-mgi-trace.txt`) shows `free` reaching 0.00 at allocated 37.93 GiB; the next layer fails the check **[V]**.
2. **`mem_get_info` charges 2 GiB of "free" for every 1 GiB allocated.** Plain script, 1 GiB `torch.empty` + `fill_` + `synchronize`, repeated: consumed (total - free) was 7.31 GiB after 4 GiB, 15.31 after 8, 31.31 after 16, 63.31 after 32, 76.79 (free 0) after 39 GiB **[V]** (`scripts/windows/probes/hip_alloc_sync_sweep.py`). It is not specific to the loader.
3. **Windows itself counts 1:1.** Holding 16 GiB: per-process "GPU Process Memory" shared usage 16.15 GiB, dedicated 0.19, total committed 16.34; physical free RAM fell by about 16 GiB (107 to 90.7) **[V]**. So the doubling is inside the HIP runtime's accounting, not in what Windows allocates. Cause **[?]**.
4. **Allocations go on succeeding after `free` hits 0, then the context dies.** Plain sweep: 60 allocations fine, the 61st (or its sync) raises `hipErrorLaunchFailure` (error 719, "unspecified launch failure"); afterwards even `empty_cache()` raises **[V]**. An earlier 256 MiB-chunk sweep reached 101.25 GiB of allocations before `free: 0` OOM, then 719 on `empty_cache()` **[V]**; the 101 GiB figure is therefore not usable memory, only address space that was handed out.
5. **The real limit is lower in the loader.** With the headroom check disabled (`EXL3_AUTOSPLIT_MARGIN_MB=-90000`) the load went from 38 to 43 GiB (layers 28-32), then died with error 719 inside `MultiLinear.__init__` (`torch.tensor(..., device=...)`, `exllamav3/modules/multilinear.py:30`) **[V]**. So bypassing the check does not help: the GPU context is lost at about 43 GiB allocated in the loader (about 60 GiB in the plain sweep) **[V]**.
6. **WDDM budget (DXGI, `scripts/windows/probes/dxgi_budget.ps1`, read-only)** **[V]**: AMD adapter dedicated 0.33 GiB, shared-system 101.72 GiB; `QueryVideoMemoryInfo` local segment budget **101.30 GiB**, available for reservation 50.77 GiB, non-local budget 0. The numbers did not move while another process held 8 or 32 GiB. So Windows offers about 101 GiB, HIP reports 76.79 GiB total, and contexts die at 43 to 60 GiB: three different numbers.
7. **Fragmentation test (fresh process per chunk size, each chunk filled and synchronised)** **[V]**: first failure after 55 GiB with 256 MiB chunks, 55 GiB with 1 GiB chunks (61 GiB in the earlier run), 60 GiB with 4 GiB chunks, 48 GiB with 16 GiB chunks (the 4th chunk fails), always error 719, never a normal OOM. Small chunks do not do better than large ones, and the point moves 5 GiB between identical runs, so address-space fragmentation of the allocator does not explain it; the threshold looks like a roughly 55 to 64 GiB wall that something else moves **[I]**. A fragmentation effect inside the driver's own page tables or GART remains possible and is not excluded **[?]**.
8. Old finding that still matters: S1-04 measured 100 GiB "allocatable" in dedicated mode and `mem_get_info` totals of 107.87 GiB. In dedicated mode the 96 GiB pool really was usable (122B 61 GiB and Flash-Next 64 GiB loaded) **[V, journal]**.

## HIP runtime source, read 2026-11-20 (ROCm/rocm-systems `develop` @ `3ac14f9`, 2026-11-20; shallow sparse clone of `projects/clr` in the session scratchpad, not in the repo)

- The 2:1 accounting is a known, fixed bug: [rocm-systems#13193](https://github.com/ROCm/rocm-systems/pull/13193), commit `dc313808f`, merged **2026-11-02**, "stop double-counting APU allocations in hipMemGetInfo" (JIRA ROCM-32243). `Device::globalFreeMemory()` (`projects/clr/rocclr/device/pal/paldevice.cpp`, ~line 2027) charged an aperture (GART) allocation twice on an APU: once through PAL's per-heap `allocedMem` and once through the OS budget query, because the KMD reports aperture allocations in the *local* segment group. Commit text: Windows APUs lose "twice the size of every allocation that spills out of the device-local carve-out" and "allocations keep succeeding after reported free reaches 0". The fix sums the segment groups and compares once. **[V: source]** It also notes `freeMemory[0]` gates PAL's allocation fallback loop (`palmemory.cpp:114-133`), so under-reporting can abandon retries that had memory.
- Our local numbers fit that description: the first (largest) allocation counts 1:1, every later one 2:1: 1x8 GiB consumed 8.15 GiB; 2x4 GiB 12.15; 8x1 GiB 15.15; 32x256 MiB 15.90; 512x16 MiB 15.97 **[V]**.
- Total and max-allocation reporting: [rocm-systems#10974](https://github.com/ROCm/rocm-systems/pull/10974), commit `b4bb73c1c`, merged **2026-09-04**: PAL discounted the GART aperture by 25% and clamped the max single allocation to 64 GiB; the fix credits `gart - min(gart/4, 4 GiB)`, sets `maxMemAllocSize_` to the whole pool and raises `maxAllocSize_` to 256 GiB (`palsettings.cpp:216`). The PR text says `hipMemGetInfo` also saturates at zero free because of the same discount. **[V: source, PR text read via subagent]**
- **Our runtime predates both fixes.** Installed `amdhip64_7.dll` 10.0.3581.0 (wheel `rocm 10.1.0a20260822`, built 2026-08-22) is the one torch loads **[V]**; #10974 merged 2026-09-04 and #13193 on 2026-11-02. The driver's `C:\Windows\System32\amdhip64_7.dll` is newer (10.0.3683.0), but preloading it before `import torch` segfaults (exit 139) **[V]**; swapping it in is not a quick fix.
- **No newer public wheel found.** Newest Windows `torch`/`rocm`/`therock-dist-windows-gfx1151` on `https://rocm.nightlies.amd.com/whl-multi-arch/` and `tarball-multi-arch/` is `10.1.0a20260822` (what we run); `whl-staging-multi-arch`, `v2` and `v2-staging` hold older 7.x builds **[V]**. PyPI `rocm` has only 0.1.0 **[V]**. The 10.1.0 release (2026-10-05) and a 10.2 branch (mentioned in rocm-systems commit `752f17409`) exist, but I did not find where Windows packages for them are published **[?]**.
- **Not explained by this fix:** the error 719 (context lost) at 43 to 60 GiB. The PR says reporting was wrong, "rather than the memory being exhausted", and it does not touch the launch-failure path. TheRock #8922 shows 719 after about 100 GiB at small VGM. Whether newer runtimes still die at 43 to 60 GiB is unknown **[?]**; it needs a test with a post-fix runtime.

To test: count host-registered bytes in the loader; repeat the plain sweep with a large `hipHostRegister`/pinned allocation held first and see whether the device-only failure point drops by the same amount. A smaller VGM (or a different OS-visible RAM) would show whether the limit scales with RAM (TheRock #8922: max allocation "follows RAM visible to Windows").

### Test of the mapped-host-memory hypothesis (built runtime, 2026-11-20) **[V]**

- Host memory held first, then a device sweep (1 GiB chunks, filled and synchronised) until error 719: no host memory **61 GiB**; **16 GiB pinned** (`pin_memory=True`) **44 GiB**; **32 GiB pinned 29 GiB**; **32 GiB pageable** (plain `torch.ones`) **45 GiB**. Pinned host memory therefore counts 1:1 against the same ~61 GiB limit as device memory; pageable host memory counts about half (16 GiB lost per 32 GiB held) **[V]**, reason unknown **[?]**. Script: `pin.py` pattern in the journal entry, results only here.
- Same wall for every device allocation API, called directly through `hipMalloc`, `hipExtMallocWithFlags` (fine-grained and uncached) and `hipMallocManaged`: 60 to 61 GiB, then error 719 on the next memset/sync **[V]**. `hipHostMalloc` (pinned host, written by a device `hipMemset`) died at 45 GiB **[V]**. So the limit is below the runtime (kernel-mode driver / WDDM mapping), not in one allocator path; the shared (non-local) segment, not a PAL heap choice.
- The loader's own 719 depends on the run: 35 GiB (first run after other crashes), 59.9 GiB at layer 45 (second run, `loaddiag` 48 modules, then `stloader: device sync failed: unspecified launch failure`) **[V]**. The loader's pinned pool is only 128 MiB (`stloader.h`: 8 threads x 4 slots x 4 MiB), so the loader is not hiding extra mapped memory; it simply meets the same ~60 GiB wall **[V]**. Free physical RAM was still 41 GiB when the context died **[V]**, so this is not RAM exhaustion.
- Consequence: with the physical GPU-mapped budget at about 60 GiB (device + pinned, pageable at half), Flash-Next 4.05bpw (about 64 GiB of device weights plus cache) cannot load in dynamic mode on this OS/driver, and the 122B (61 GiB) is at the edge. 35B, 27B and 9B fit. The wall is also lower than TheRock #8922's 100 GiB at 0.5 to 1 GiB VGM on the same chip and OS build, so something differs on this machine **[?]**: driver version (32.0.32015.7029 here vs 32.0.31041.5005 there), the runtime build, page-file or commit settings, or the BIOS/Adrenalin "dynamic" setting.

### Trace of the failure (`AMD_LOG_LEVEL=1/4`, rebuilt runtime, `hipMalloc` loop) **[V]**

- At the wall the runtime logs `PAL failed to submit CMD! result:-5`, then `PAL failed to finalize a command buffer! result: -28`. In PAL's `Result` enum (`shared/amdgpu-windows-interop/pal/inc/util/palUtil.h`) -5 is **`ErrorOutOfGpuMemory`** and -28 is `ErrorIncompleteCommandBuffer` (a consequence). The -5 comes from `iQueue_->Submit()` (`projects/clr/rocclr/device/pal/palvirtual.cpp:460`), i.e. the submit to the Windows graphics kernel (WDDM/VidMm) is refused as out of GPU memory. Later: `PAL reports the device unusable! result:-5` (`paldevice.cpp:2480`) and every HIP call returns 719. So 719 is the user-mode symptom of an OS-level out-of-GPU-memory on submit, with 41 GiB of RAM free.
- HIP makes every allocation permanently resident (`alwaysResident_`, `AddGpuMemoryReferences(..., GpuMemoryRefCantTrim)`, `palresource.cpp:35`, `palsettings.cpp:113`), so VidMm must keep all of it resident for every submit. Setting `PAL_ALWAYS_RESIDENT=0` (runtime flag) does **not** move the wall: still 61 GiB and `result:-5` **[V]**.
- No System or Application event-log entry (dxgkrnl, amdkmdag, TDR, Windows Error Reporting) around the failures **[V]**; this is a refused submit, not a driver reset.
- Numerology **[I]**: DXGI shared-system 101.72 GiB = 0.80 x 127.15 GiB OS-visible RAM; the wall of about 61 GiB is 0.60 x 101.72 GiB, or 0.48 x RAM. The TheRock maintainer's 60.32 GiB total on Windows 22H2 (WDDM 3.1) points at the same figure. A fixed fraction of RAM for what VidMm will keep resident for one process/adapter is the working explanation; I have not found where Windows or the AMD KMD defines it.
- Conclusion: the wall is outside user space (kernel-mode driver / VidMm policy); our runtime change cannot raise it. Remaining levers: a different Windows/driver build (TheRock #8922 saw 100 GiB on a similar setup), a different VGM/UMA setting, or an AMD fix. A direct measurement of the real segment limit would be `D3DKMTQueryStatistics` (segment `CommitLimit` / `BytesCommitted`), not done yet.

### WDDM segments (`D3DKMTQueryStatistics`, `scripts/windows/probes/wddm_segments.cpp`, built with MSVC against SDK 10.0.28000, read-only) **[V]**

- AMD adapter, 4 segments: #0 local, CommitLimit **0.33 GiB** (the dedicated carve-out); #1 aperture, **7.98 GiB**; #2 aperture, **119.17 GiB**; #3 aperture, CommitLimit effectively unlimited (1.7e10 GiB). Second adapter (Microsoft Basic Render Driver): one 127.15 GiB aperture segment. TDR count 0.
- During the sweep all HIP allocations land in **segment #3**: BytesCommitted 30.23 GiB when 30 GiB were held. At the failure (error 719 after 61 GiB) segment #3 shows **BytesResident 61.33 GiB**, then drops to 0.04 GiB committed once the context is lost. Segments #1 and #2 stay at 0 to 0.26 GiB.
- So no advertised segment limit is reached (#3 has no limit, #2 has 119 GiB, nothing is near its CommitLimit). The refusal comes at about **61.3 GiB resident in an unlimited aperture segment**, i.e. a policy of VidMm or the AMD KMD on how much system memory may be kept resident (locked) for the GPU, not a configured segment size. The DXGI budget (101.3 GiB) and Task Manager's 102 GB shared figure are not the enforced limit. 61.33 GiB is 0.482 x the 127.15 GiB OS-visible RAM **[V: numbers; I: the RAM-fraction reading]**.
- Not found on this machine: any registry value or Windows setting for that cap (GraphicsDrivers, MemoryManager). Searching AMD's driver keys and the Windows "locked pages" accounting for a 0.48 factor would be the next lead; the AMD maintainer's report that the same chip reaches 108 GiB at 96 GiB VGM and 100 GiB at 0.5 GiB VGM on 26H2 suggests the cap is not universal **[?]**.

### Does the ROCm/HIP/PAL layer expose the limit? **No** **[V]**

- HIP API: `hipDeviceGetAttribute` scanned over attributes 0 to 399 and 10000 to 10099, `hipDeviceGetLimit` 0 to 11, `hipMemGetInfo`: nothing near 61 GiB (the only large values are 2 GiB grid maxima; total 98.22 GiB, free 98.07 GiB).
- PAL (the layer that talks to the Windows kernel), read with a temporary local print in the scratch clone's `paldevice.cpp` (not in any repo, rebuild only): heaps Local 0.327 GiB (physical 0.5), Invisible 0, **GartUswc 101.719 GiB, GartCacheable 101.719 GiB**; `maxPhysicalMemSize` 102.219 GiB, `maxLocalMemSize` 0.327 GiB, `maxVirtualMemSize` 65512 GiB, `barSize` 0.5 GiB; OS budget query (`QueryGpuMemoryBudgetInfo`) group 0 usage 0, **budget 101.295 GiB**, group 1 budget 0 **[V]**. Every figure PAL or HIP reports is about 101 to 102 GiB (0.8 x RAM); the HIP runtime reads only `usage`, never `budget`, and nothing in it knows about a 61 GiB residency limit.
- The only trace of the limit is the failed submit (`result:-5`, `ErrorOutOfGpuMemory`) and the WDDM segment statistics above. A runtime that wanted to avoid the wall would have to track resident bytes itself and stop at an assumed ~61 GiB; there is no API to ask.

Next experiments (cheap): (1) the same sweep with the stock runtime but old/new driver is not possible without reinstalling; instead run `scripts/windows/probes/dxgi_budget.ps1` while the sweep holds 50 GiB to see whether WDDM's budget or usage changes near the wall; (2) set `AMD_LOG_LEVEL=4` on the 719 and read the last PAL/KMD message (TheRock maintainer's request); (3) check `Get-WinEvent` System log for a dxgkrnl/amdkmdag TDR or VidMm entry at the failure time (none seen so far, not searched at the exact timestamps); (4) test a second VGM value if the operator is willing.

## Working hypotheses **[I]**

1. HIP on Windows backs `hipMalloc` with WDDM shared (system) memory in dynamic mode, and HIP's own free-memory estimate (`total - used*2`?) double counts. The 2:1 slope is exact, which points to a deliberate or accidental double bookkeeping (for example VA reservation plus commit, or a local plus a non-local mapping of the same allocation).
2. A second, real limit exists around 60 GiB (plain) or 43 GiB (loader, which also pins host memory and registers mmap-ed shards) and kills the context with 719. It may be the WDDM shared-segment budget (the maintainer's 60.32 GiB total on WDDM 3.1 is suspiciously close to our plain-sweep 60 GiB) rather than the 76.79 GiB `hipMemGetInfo` reports.
3. If so, Flash-Next 4.05bpw (about 64 GiB of GPU weights plus cache) cannot load in dynamic mode at all; the 122B (61 GiB) is borderline; the 35B and 27B fit.

## What we can do without Fable (cheap, reversible)
